## 8. Conclusions

- **Mustard/drill**: the recovery-condition (unperturbed re-execution of the critic's own top-1 pick) rate closely tracks the confirmatory-300 baseline for both objects (CIs overlap, two-proportion test not significant) -- this **cross-validates `collect_recovery_data.py`'s candidate-selection and execution pathway** against the already-verified Phase 1/2/C.3 pipeline, rather than resting on an unverified new code path.
- **Cracker**: the std=0.02 recovery rate (12.3%, 95% CI covers the 18.0% baseline) is **below the confirmatory-300 baseline but the confidence interval covers it** -- this must not be described as a significant degradation. It is consistent with cracker's already-established high-variance, low-base-rate behavior (Section 1's integrity check and the original circuit-breaker investigation both point the same way), not a demonstrated regression.
- **`recovery_success` is a dataset statistic, not a validated policy improvement.** No comparison against a no-recovery or geometry-only control arm was collected in this pass; nothing here supports a claim that the 'return to nominal' recovery mechanism is effective versus any alternative.
- **C.7's actual contribution at this point**: a working, cross-validated perturb-then-recover data collection pipeline, and a stratified dataset (6 conditions, 265 total trials) with documented reproducibility metadata (`frozen_config.json`/`frozen_config_append_*.json` per directory) and a clean integrity check (Section 1) -- an infrastructure and dataset contribution, not yet an efficacy result.
